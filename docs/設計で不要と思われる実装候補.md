# 設計（SAS / SPL / Async-First）に照らして**不要または縮小検討すべき実装候補**

📌 目的：このドキュメントは「Rustカーネル設計案（SAS/SPL/Async-First）」に基づき、現在のカーネル実装内で**この用途（ExoRust設計）には不要、または設計に合わないため削減・移行を検討すべきコード**の候補を短く整理したものです。

---

## 要約（TL;DR） ✅

- 高優先で検討すべきは **プロセスモデル／procfs／POSIXシグナル／プロセス別ページテーブル** に関する実装。これらはSAS/SPLの設計哲学と重複または矛盾します。
- 推奨アプローチ：
  1. `posix-compat` 等の機能フラグで互換レイヤを隔離
  2. 依存箇所を `Domain/Cell`（または `TaskHandle`）へ段階的に移行
  3. 互換レイヤを削除（段階的）

---

## 優先候補（短表） 🔎

| 優先度 | ファイル / モジュール | 要点（なぜ不要か） | 影響(代表的参照) | 推奨アクション |
|---:|---|---|---|---|
| 高 ✅ | `kernel/src/task/process.rs` | フルなプロセス（PID/ppid/fork/exec/credential/rlimit）モデル。SASでは不要／冗長 | 多数（`fs/procfs.rs`, `ipc/shared_mem.rs`, `net/udp.rs`, `service_impl.rs`, shell namesp.`）` | 機能フラグ化→`DomainId` へ段階移行→非推奨→削除（大規模リファクタ） |
| 高 ✅ | `kernel/src/fs/procfs.rs` | `/proc/[pid]` 等のプロセス中心ツリー（プロセス依存情報） | デバッグツール／一部サービス | 保守する必要があるsystem-levelエントリは残す（`/proc/meminfo`等）。`/proc/[pid]` を `sys/cell` に置換または機能フラグ化 |
| 高 ✅ | `kernel/src/task/signal.rs` | POSIXシグナル集合・ハンドラ機構（SIGCHLD 等） — 設計上不要／冗長 | `task` モジュール内部、少数のランタイムロジック | 内部通知（`SIGWAKE` 等）のみ残し、POSIX互換部分を削除または互換レイヤに移動 |
| 高 ✅ | `kernel/src/mm/address_space.rs` + `mm/rcu_vma.rs` | プロセス毎のページテーブル・ASID・fork/exec 支援 | MMコア（`thp_promotion` 等）に依存 | 保持すべきはグローバルマッピング／ガードページ機能。ASID/CR3切替・fork/execは `posix-compat` へ移す（段階的削除） |
| 中 ✅ | `kernel/src/mm/mmap.rs` (プロセス依存部分) | path-based per-process mmap semantics | 一部ファイルマッピングコード | ファイル→メモリマッピングは維持。per-process semantics を Domain-aware にリファクタリング |
| 中 | `proc` 関連のユーティリティ（小さな helper） | デバッグ以外では不要な箇所あり | ツール／shell | 移行またはテスト用に限定して残す |

## 詳細（候補ごと） 🔧

### 1) `kernel/src/task/process.rs` — フルプロセスモデル (最優先)

- なぜ不要か：SAS/SPL は単一アドレス空間＋言語ベース分離を前提とするため、PID/fork/exec/プロセスグループ等は設計上不要または設計に逆行する。
- 代表的依存箇所（検出例）: `kernel/src/fs/procfs.rs`, `kernel/src/ipc/shared_mem.rs`, `kernel/src/net/udp.rs`, `kernel/src/service_impl.rs`, `kernel/src/shell/**`。
- リスク：高（多数の参照・MM/FS/IPCに波及）。
- 推奨アクション：
  1. 互換 API を `#[cfg(feature = "posix-compat")]` 下へ移動。
  2. 主要依存箇所を `DomainId` / `TaskHandle` ベースの実装へ段階移行（薄い shim を用意）。
  3. `process.rs` を小さく分割（metadata-only / legacy-compat / removal-ready）して逐次削除。
- 受け入れ条件（acceptance）：全カーネルコンポーネントが `ProcessId` を参照せずにビルド可能、主要ユースケースの e2e テスト通過。

### 2) `kernel/src/fs/procfs.rs` — /proc のプロセスツリー

- なぜ不要か：`/proc/[pid]` はプロセス概念に依存。SAS では `cell`/`domain` ビューに置換可能。
- 残すべきもの：`/proc/meminfo`, `/proc/cpuinfo`, `/proc/uptime` 等のシステムメトリクスは有用。
- 推奨アクション：
  - Split: `procfs::system` (keep) + `procfs::process` (deprecated)
  - `procfs::process` を `sys/cells` にマップする移行レイヤを提供

### 3) `kernel/src/task/signal.rs` — POSIXシグナル

- なぜ不要か：設計は async/await と Result/Err ベースのエラー通知を推奨。POSIXシグナルは非整合かつ複雑。
- 推奨アクション：
  - **残す**：内部通知用の最小セット（`SIGWAKE`, `SIGDOMAIN`, `SIGIPC`）
  - **削除/置換**：`SIGCHLD`, `SIGSTOP`, `sigaction` の互換レイヤは機能フラグ下へ移動

### 4) `kernel/src/mm/address_space.rs` 系 — プロセス用ページテーブル

- なぜ不要か：SAS では CR3 切替／ASID 管理は主目的を失う（例外はガードページ・IOMMU・個別保護）。
- 残すべき機能：ガードページ、W^X、メモリプール、ファイル→メモリマッピング primitives
- 推奨アクション：
  - ページテーブルの「プロセス別ルート」部分を削除/機能フラグ化
  - Mapping 管理を GlobalMapping Manager に統合

## 影響把握（短い影響マップ）🗺️

- 直接依存（例）: `kernel/src/fs/procfs.rs`, `kernel/src/ipc/shared_mem.rs`, `kernel/src/net/udp.rs`, `kernel/src/service_impl.rs`, `kernel/src/shell/**`。
- テスト: 単体テスト・e2e テストの一部が `procfs` / `process` に依存している可能性あり → 依存テストの洗い替えが必須。

---

## 移行 / 削除の実務チェックリスト（短期プラン） ⏭️

1. ガードレール: `feature = "posix-compat"` を導入し、既存のプロセス/POSIX API をそこに移動（短期：**非破壊**）。
2. Shim 層: `ProcessId -> DomainId` の薄い変換 shim を実装（依存先を順次切り替える）。
3. ドキュメント: `docs/ARCHITECTURE.md` に「非推奨 API リスト」と「移行パス」を追記。
4. テスト: 互換フラグ ON/OFF 両方で CI を回す（互換OFFがレポジトリのデフォルトで通ることが目標）。
5. 段階削除: 依存が無くなったモジュールを削除（PR 毎に小分け）。

短期（1–2 sprint）優先タスク：

- 追加：`posix-compat` feature + deprecation warnings
- 作成：`docs/migration-posix-→-domain.md`（移行手順）
- テスト：`procfs` に依存する e2e を `posix-compat` に紐付け

## 具体的なコマンド（レビュア向け／開発者向け） 🛠️

- 影響箇所検索（ローカル）:
  - rg を推奨: `rg "\bProcessId\b|procfs|SIGCHLD|fork\(|execve" --hidden`
  - git grep: `git grep -n "ProcessId\|procfs\|SIGCHLD"`
- 互換フラグのビルド検査:
  - 互換OFF: `cargo build --workspace --features "default" --no-default-features`
  - 互換ON: `cargo build --workspace --features posix-compat`

## リスク評価と推定工数（概算） 📆

- `process.rs` の段階的削除: **高リスク / 2–4 週間（分割PRで対応）**
- `procfs`（/proc/[pid] 削除）: **中リスク / 1–2 週間（移行とテスト）**
- `signal.rs` の削減: **中リスク / 1 週間**
- `address_space.rs` の整理（ASID/CR3 部分）: **高リスク / 2–3 週間**

## 推奨次アクション（優先順位付き） ✅

1. `posix-compat` feature を作成し、`process.rs` / `signal.rs` / `/proc/[pid]` をそこへ移す（安全な切り分け）
2. コアチームで Impact review（参照一覧 + e2e の洗い出し）を実施
3. `DomainId` 移行の最小 PR（`ProcessId` → `DomainId` shim + 1 つのサブシステム移行）を提出
4. 互換OFF を CI のデフォルトにして段階的に不要コードを削る

## 最後に — 要約（1行）

プロセス中心・POSIX互換の実装は、ExoRust の SAS/SPL 設計では**段階的に廃止／機能フラグ化→Domainベース実装へ移行**するのが安全かつ効果的です。まずは `posix-compat` 機能フラグで隔離し、影響範囲を小さな PR 単位で潰していくことを強く推奨します。⚡
